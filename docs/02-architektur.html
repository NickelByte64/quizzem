2 · Architektur & Techstack

Ein einzelner Node.js-Prozess als autoritativer Spielserver, Echtzeit über native WebSockets, Spielzustand im Arbeitsspeicher, Quizzes als JSON-Dateien. So einfach wie möglich – und für dieses Szenario genau richtig.

Leitprinzipien

  1. Ein Prozess, ein Rechner. Alles läuft auf dem Laptop des Quizmasters. Keine Datenbank, kein Docker, keine Cloud. Damit entfällt 80 % der üblichen Komplexität.
  2. Der Server ist die einzige Wahrheit. Der komplette Spielzustand (Phase, Antworten, Punkte) lebt ausschließlich im Server. Clients sind „dumme“ Renderer, die Zustands-Snapshots anzeigen und Absichten („ich antworte B“) melden. Das macht Reconnect trivial und Schummeln unmöglich.
  3. Klein dimensioniert, bewusst. 40 Teilnehmer, die alle 30 Sekunden eine Antwort schicken, sind für einen Node-Prozess Leerlauf. Es braucht keine Skalierungs-Architektur – es braucht Robustheit gegen wackliges WLAN.

Systemübersicht

Techstack & Begründung

Baustein Wahl Warum (für dieses Projekt)
Runtime Node.js LTS (≥ 22) Vorgabe. Event-Loop passt perfekt zu „viele Verbindungen, wenig Rechenarbeit“.
Sprache TypeScript Ein gemeinsames shared/-Paket typisiert alle Socket-Events und den Spielzustand – Client und Server können gar nicht auseinanderlaufen. Für einen Solo-Dev der billigste Bug-Schutz überhaupt.
HTTP-Server Express 5 Braucht fast nichts können: statische Dateien ausliefern + 2–3 REST-Routen für den Quiz-Editor. Express ist das am besten dokumentierte Werkzeug dafür. (Fastify wäre schneller – Performance ist hier aber irrelevant.)
Echtzeit Native WebSockets (ws auf dem Server, Browser-WebSocket-API im Client) Standardnah, ohne Abstraktionsschicht und ohne eigenes Wire-Protokoll. Der Preis: Reconnect und Heartbeat bauen wir selbst (~100 Zeilen, einmalig in client/src/lib/ws.ts bzw. serverseitigem Ping/Pong) – im Kneipen-WLAN sind das Kernfeatures, siehe Robustheit. Alle Nachrichten sind JSON im Umschlag { type, payload }, typisiert in shared/.
Frontend Vite + React Bekanntes Werkzeug des Entwicklers – für einen Solo-Dev das stärkste Argument überhaupt. Vite baut beide Ansichten als statische Dateien, die Express ausliefert. Die Architektur („Zustands-Snapshot rein, UI raus“) ist Framework-neutral.
Client-State zustand Ein einziger Store hält den jeweils letzten Server-Snapshot plus lokalen UI-Zustand (z. B. „Antwort abgeschickt“). Jede WebSocket-state-Nachricht ruft einmal setState auf, die Komponenten subscriben gezielt. Mehr Client-State-Management braucht diese App nicht.
Spielzustand In-Memory (ein JS-Objekt) Eine Session lebt Minuten bis Stunden auf einem Rechner. Eine Datenbank würde nur Komplexität addieren. Stürzt der Server ab, ist die Session weg – akzeptables MVP-Risiko (Absicherung: siehe Backlog „Session-Snapshot“).
Quiz-Speicherung JSON-Dateien in ./quizzes/ Menschenlesbar, per Git versionierbar, trivial zu sichern und von Hand editierbar, falls der Editor mal klemmt.
QR-Code npm-Paket qrcode Erzeugt den Beitritts-QR serverseitig als Data-URL – funktioniert offline.
Tests Vitest Ein Test-Runner für Client und Server. Fokus: GameEngine und Scoring als reine Funktionen testen – da stecken die Fehler, die einen Quizabend ruinieren.

│       │   └── scoring.ts    # Punkteberechnung (reine Funktion)

├── client/
│   └── src/
│       ├── host/             # Quizmaster-Ansicht (Editor, Lobby, Steuerung)

Wichtigste Regel der Struktur: engine.ts und scoring.ts kennen weder WebSockets noch Express. Sie sind reine Funktionen: (zustand, aktion) → neuer Zustand. Dadurch sind sie ohne Netzwerk testbar – und genau dort liegt die Logik, die stimmen muss.

Spielablauf als State-Machine

Timer als Substate von QUESTION: Beim Anzeigen der Frage ist questionEndsAt = null – Antworten sind bereits möglich, aber es läuft noch keine Uhr. Erst wenn der Quizmaster „Timer starten“ drückt (sofort oder z. B. nach dem Vorlesen der Frage), setzt der Server questionEndsAt = jetzt + timeLimitSec und broadcastet den neuen Snapshot – ab da läuft auf allen Geräten der Countdown. Timer-Ablauf oder „alle haben geantwortet“ löst REVEAL aus; manuell auflösen kann der Quizmaster jederzeit, auch ganz ohne Timer.

Nachrichten-Protokoll (WebSocket)

Jede Nachricht ist ein JSON-Objekt im Umschlag { type: string, payload: object }. Alle Typen sind als diskriminierte Union in shared/src/messages.ts definiert – Client und Server parsen und versenden ausschließlich über diese Typen.

Client → Server

Message-Typ Sender Payload Wirkung
player:join Teilnehmer { sessionId, name, playerId? } Beitritt bzw. Reconnect (mit vorhandener playerId aus localStorage).
player:answer Teilnehmer { questionIndex, optionIndex } Antwort abgeben. Server prüft: richtige Frage? Timer offen? Noch nicht geantwortet?
host:createSession Quizmaster { quizId } Session anlegen, Join-URL + QR zurückgeben.
host:start Quizmaster – LOBBY → erste Frage.
host:startTimer Quizmaster – Startet den Countdown der aktuellen Frage (questionEndsAt wird gesetzt).
host:reveal Quizmaster – Frage schließen und auflösen (jederzeit, auch ohne/vor Timer-Ablauf).
host:next Quizmaster – Scoreboard → nächste Frage bzw. FINAL.

Server → Clients

Message-Typ Empfänger Payload (Kern)
state alle (Broadcast) Der komplette, rollenspezifisch gefilterte Zustands-Snapshot – siehe unten.
player:answerAck einzelner Teilnehmer { accepted: boolean } – sofortige Bestätigung fürs UI.
error einzelner Client { code, message } – z. B. „Name schon vergeben“.

Eine Nachricht statt zwanzig: Nach jeder Zustandsänderung broadcastet der Server einfach den neuen Snapshot als state. Clients rendern stumpf, was ankommt (im zustand-Store: ein setState pro Nachricht). Das eliminiert die ganze Klasse von „Client hat Nachricht X verpasst“-Bugs – und ein frisch verbundener (oder reconnecteter) Client ist mit dem ersten state sofort synchron.

Rollenfilter als Fairness-Garantie: Der Snapshot für Teilnehmer enthält während QUESTION nur Fragetext und Optionen – nie die richtige Antwort. Die kommt erst im REVEAL-Snapshot. Der Quizmaster-Snapshot enthält zusätzlich Antwortstatistik („17 von 23 haben geantwortet“).

Datenmodell

// shared/src/types.ts (Auszug)

interface Quiz {
  id: string;
  title: string;
  questions: Question[];
}

interface Question {
  text: string;
  options: string[];        // 2–6 Antwortoptionen
  correctIndex: number;     // genau eine richtige
  timeLimitSec: number;     // Default 30
  points: number;           // Default 100
}

interface GameState {
  phase: "LOBBY" | "QUESTION" | "REVEAL" | "SCOREBOARD" | "FINAL";
  quiz: Quiz;
  currentQuestionIndex: number;
  questionEndsAt: number | null;   // null, bis der Host den Timer startet;
                                   // danach Unix-Timestamp – Clients rechnen selbst runter
  players: Map<string, Player>;    // key: playerId
}

interface Player {
  id: string;               // vom Server vergeben, Client speichert in localStorage
  name: string;
  score: number;
  answers: (number | null)[];      // gewählter optionIndex je Frage
  connected: boolean;
}

Performance & Robustheit im Hotspot-Szenario

Die eigentliche Herausforderung ist nicht Last, sondern instabiles WLAN und Handy-Browser, die Tabs einfrieren. Diese fünf Entscheidungen adressieren das:

  1. Serverseitiger Timer, keine Tick-Broadcasts. Beim Timerstart verschickt der Server einmal questionEndsAt (Timestamp); jeder Client rechnet die Restzeit lokal herunter. Kein „jede Sekunde ein Broadcast an 40 Geräte“ – und ob eine Antwort rechtzeitig kam, entscheidet allein die Server-Uhr.
  2. Selbst gebauter Reconnect als Kernfeature. Da wir rohe WebSockets statt Socket.IO nutzen, liegt der Reconnect bei uns – einmalig gebaut in client/src/lib/ws.ts: bei close/error neu verbinden mit exponentiellem Backoff (0,5 s → max. 5 s), beim Wiederverbinden die playerId (localStorage) per player:join mitschicken. Der Server ordnet sie dem bestehenden Player-Objekt zu und antwortet mit dem aktuellen Snapshot – Display aus → Display an → weiterspielen. Serverseitig erkennt ein Ping/Pong-Heartbeat (alle 15 s) tote Verbindungen und markiert Spieler als connected: false.
  3. Kleine Payloads. Der Teilnehmer-Snapshot enthält keine Spielerliste mit allen Antworten, sondern nur: Phase, Frage, eigener Punktestand, Top-Scoreboard. Bei 40 Geräten im 2,4-GHz-Hotspot zählt jedes Kilobyte.
  4. Idempotente, validierende Handler. Jedes eingehende Event wird gegen den Zustand geprüft (richtige Frage? Phase offen? schon geantwortet?). Doppelte oder verspätete Events werden still verworfen – wackliges Netz erzeugt genau solche Duplikate.
  5. Statisches Frontend, einmal geladen. Vite-Build als kleine statische Dateien (Ziel: < 200 kB), danach läuft alles über die eine WebSocket-Verbindung. Kein Nachladen mitten im Spiel.

Netzwerk-Setup am Quizabend

Ablauf für den Quizmaster

  1. Windows: Einstellungen → Netzwerk → Mobiler Hotspot aktivieren (Name + Passwort einmalig festlegen).
  2. App starten: npm start – der Server bindet an 0.0.0.0:3000, ermittelt die eigene Hotspot-IP und zeigt die Join-URL samt QR-Code in der Host-Ansicht an.
  3. Teilnehmer: Hotspot-WLAN beitreten → QR scannen → Name eingeben → spielen.
Bekannte Stolpersteine (im Feldtest, Phase 5, explizit prüfen):
  • Windows-Firewall: Beim ersten Start fragt Windows nach Netzwerk-Freigabe für Node – „Privates Netzwerk“ erlauben, sonst erreicht kein Handy den Server.
  • Hotspot-Gerätelimit: Der Windows-Mobile-Hotspot erlaubt oft nur 8 Geräte gleichzeitig. Für größere Runden: einen kleinen Reise-Router (~30 €) mitnehmen und den Laptop per Kabel/WLAN dranhängen – die App ändert sich dadurch nicht.
  • Kein HTTPS nötig – und das ist gut so: Im lokalen Netz über IP-Adresse ist HTTP der reibungsloseste Weg. Selbstsignierte Zertifikate würden auf jedem Handy Warnungen produzieren.
  • „Kein Internet“-Warnung: Handys melden im Hotspot ohne Uplink gern „Verbunden, kein Internet“ und fragen, ob man verbunden bleiben will – die Teilnehmer-Ansicht sollte in der Join-Hilfe kurz darauf hinweisen.

Bewusst verworfene Alternativen

Alternative Warum verworfen
Cloud-Hosting (z. B. Railway, Fly.io) Widerspricht dem Kernszenario „funktioniert im Keller einer Kneipe ohne Internet“. Kann später als Option dazukommen – die Architektur (ein Node-Prozess) ist dafür bereits deploybar.
Datenbank (SQLite, Postgres) Es gibt keine Daten, die eine Session überleben müssen, außer Quizzes – und die sind als JSON-Dateien besser aufgehoben (editierbar, versionierbar).
Socket.IO statt nativer WebSockets Brächte Reconnect, Heartbeat und Long-Polling-Fallback fertig mit – dafür ein eigenes Wire-Protokoll und eine Abstraktionsschicht auf beiden Seiten. Entscheidung: standardnah bleiben und Reconnect/Heartbeat selbst bauen (~100 Zeilen, siehe Robustheit). Der Long-Polling-Fallback ist verzichtbar: Alle relevanten Mobilbrowser können WebSockets, und es gibt keine Firmen-Proxies im eigenen Hotspot.
State-Machine-Bibliothek (z. B. XState) im Server Die GameEngine ist eine handgeschriebene State-Machine: eine diskriminierte Union für die Phasen + reine Übergangsfunktionen. Bei 5 Zuständen und einer Handvoll Übergängen wäre eine Bibliothek mehr Lernaufwand als Nutzen. Im Client übernimmt zustand das State-Management (Snapshot-Store) – eine State-Machine braucht das Frontend nicht, denn die Zustandslogik lebt komplett im Server.
Next.js / Nuxt / Full-Stack-Framework SSR, Routing-Magie und Server-Components lösen Probleme, die diese App nicht hat, und koppeln den Server an ein Framework. Express + Vite bleibt durchschaubar.
WebRTC / Peer-to-Peer Ein zentraler Server existiert sowieso (der Laptop). P2P würde nur Verbindungs-Komplexität importieren.
