3 · Schritt-für-Schritt zum MVP

Sechs Phasen vom leeren Ordner bis zum bestandenen Feldtest. Jede Phase hat ein klares Ziel, ihre User Stories, Akzeptanzkriterien und eine Definition of Done – und jede endet mit etwas, das man vorführen kann.

Wie dieser Plan gedacht ist

  • Risiko zuerst: Das technisch Unsicherste ist die Echtzeit-Spielschleife über echtes WLAN – deshalb kommt sie vor dem Quiz-Editor. Ein Editor ohne funktionierendes Spiel ist wertlos; ein Spiel mit handgeschriebener JSON-Datei ist bereits ein Quizabend.
  • Jede Phase ist demofähig: Am Ende jeder Phase kannst du jemandem etwas zeigen. Das hält die Motivation als Solo-Dev hoch und deckt Denkfehler früh auf.
  • Aufwand: Die Schätzungen gehen von Feierabend-/Wochenendarbeit aus (2–4 h pro Abend). Gesamtrahmen: ca. 4–6 Wochen nebenberuflich.
  • Arbeitsweise: Ein Git-Repository ab Tag 1, kleine Commits, main ist immer lauffähig. Kein Branching-Theater – du bist allein.
PO-Hausaufgabe vor Phase 0: Die Annahmen in der Produktvision durchgehen und festzurren. Außerdem: Schreibe dein erstes echtes Quiz (10 Fragen auf Papier oder in einer Textdatei). Es wird ab Phase 2 dein Testdatensatz – und zwingt dich früh zu merken, welche Frage-Eigenschaften du wirklich brauchst.

Phase 0 Projektfundament & Walking Skeleton · ~2–3 Abende

Ziel: Das komplette Grundgerüst steht und ein Handy im selben WLAN kann eine vom Laptop ausgelieferte Seite öffnen, die per WebSocket live ein Signal empfängt. Damit ist die riskanteste Annahme („Handys erreichen meinen Node-Server im Hotspot“) am ersten Wochenende verifiziert – nicht in Woche 5.

Aufgaben

  1. Git-Repo anlegen, npm-Workspace mit server/, client/, shared/ aufsetzen (Struktur: siehe Architektur).
  2. TypeScript, Vitest und ein Formatter (Prettier) konfigurieren – einmal, dann nie wieder anfassen.
  3. Express-Server (Backend, läuft separat via tsx), der an 0.0.0.0:3000 bindet und den Vite-Build des Frontends (client/dist/) statisch ausliefert. Vite baut nur den React-Client – das Backend wird nicht von Vite gebaut. Zwei npm-Skripte: npm run dev (Vite-Dev-Server mit Proxy auf Express, für die Entwicklung) und npm start (vite build + ein Express-Prozess für den Quizabend).
  4. WebSocket-Server (ws) einbinden: Server broadcastet jede Sekunde die Uhrzeit als JSON-Nachricht, eine Mini-React-Seite zeigt sie an.
  5. Die eine WebSocket-Anbindung des Clients bauen (client/src/lib/ws.ts): Reconnect-Schleife mit exponentiellem Backoff; dazu serverseitig Ping/Pong-Heartbeat. Dieses Modul nutzen später beide Ansichten – es ist der wichtigste Baustein des Projekts.
  6. Server ermittelt beim Start die lokale IP und loggt die erreichbare URL.
  7. Windows-Hotspot aktivieren und den Durchstich mit dem eigenen Handy testen (inkl. Firewall-Freigabe).

Akzeptanzkriterien

  • npm start startet alles mit einem Befehl.
  • Ein Handy im Hotspot-WLAN öffnet http://<laptop-ip>:3000 und sieht die live tickende Server-Uhr.
  • Handy-Display 30 s sperren und entsperren → die Uhr läuft ohne Neuladen weiter (die eigene Reconnect-Schleife greift).

Phase 1 Session, Beitritt & Lobby · ~3–4 Abende

Ziel: Der Quizmaster erstellt eine Session und Teilnehmer treten ihr bei. Beide Ansichten existieren und zeigen live dieselbe Lobby. Umgesetzte Stories: U2, U3, U4 (teilweise) aus der Produktvision.

Aufgaben

  1. Datenmodell in shared/ anlegen: Quiz, Question, GameState, Player + Event-Typen.
  2. GameEngine-Grundgerüst: Zustand LOBBY, Aktionen createSession, join, disconnect, reconnect – als reine Funktionen mit Vitest-Tests.
  3. Host-Ansicht (/host): Button „Session starten“ → zeigt Join-URL + QR-Code + Live-Teilnehmerliste.
  4. Spieler-Ansicht (/play/:sessionId): Namenseingabe → Lobby („Warten auf Start … 7 Spieler dabei“).
  5. Namensvalidierung: eindeutig pro Session, 1–20 Zeichen, mit verständlicher Fehlermeldung.
  6. Reconnect-Grundlage: Server vergibt playerId, Client speichert sie in localStorage und sendet sie bei jedem player:join mit.
  7. Der state-Broadcast-Mechanismus (ein Snapshot-Event für alles) steht ab jetzt – jede spätere Phase baut nur noch darauf auf.

Akzeptanzkriterien

  • Zwei Handys treten per QR-Code bei; beide Namen erscheinen < 1 s später auf dem Laptop.
  • Doppelter Name wird beim Beitritt abgelehnt, mit klarer Meldung auf dem Handy.
  • Browser-Tab auf dem Handy schließen und URL neu öffnen → derselbe Spieler ist wieder da (kein Duplikat in der Lobby).
  • Engine-Tests decken ab: join, doppelter Name, reconnect mit bekannter/unbekannter playerId.

Phase 2 Die Spielschleife · ~4–5 Abende · Herzstück

Ziel: Ein komplettes Quiz lässt sich durchspielen: Frage → antworten → Auflösung → nächste Frage → Ende. Punkte gibt es noch nicht. Das Quiz kommt aus einer handgeschriebenen JSON-Datei in quizzes/ – dein PO-Testquiz aus der Vorbereitung. Stories: U5, U6.

Aufgaben

  1. State-Machine vervollständigen: LOBBY → QUESTION → REVEAL → SCOREBOARD → … → FINAL (Scoreboard zeigt vorerst nur „wer hat geantwortet“).
  2. Serverseitiger Frage-Timer mit manuellem Start: Beim Anzeigen der Frage läuft noch keine Uhr (questionEndsAt = null), Antworten sind aber schon möglich. Erst der Host-Knopf „Timer starten“ setzt questionEndsAt; Ablauf oder „alle haben geantwortet“ löst automatisch REVEAL aus.
  3. Host-Steuerung: „Quiz starten“, „Timer starten“, „Auflösen“ (jederzeit möglich), „Weiter“; Anzeige der Antwortquote („12/17 haben geantwortet“) und der Restzeit.
  4. Spieler-Ansicht: Frage + große Antwort-Buttons; der Countdown erscheint, sobald der Quizmaster den Timer startet; nach Abgabe gesperrt („Antwort gespeichert ✓“); bei REVEAL Markierung richtig/falsch.
  5. Antwort-Validierung im Server: nur in Phase QUESTION, nur zur aktuellen Frage, nur einmal pro Spieler, und bei laufendem Timer nur vor questionEndsAt.
  6. Rollenfilter im Snapshot: correctIndex verlässt den Server erst ab REVEAL (siehe Architektur → Fairness).
  7. Engine-Tests für die gesamte State-Machine inkl. Timer-Ablauf und verspäteter Antworten.

Akzeptanzkriterien

  • Ein 5-Fragen-Quiz lässt sich mit 2 Handys vollständig durchspielen, ohne Neuladen, ohne Entwicklereingriff.
  • Vor dem Timerstart können Teilnehmer bereits antworten; drückt der Host „Timer starten“, erscheint der Countdown auf allen Geräten synchron.
  • Nach Timer-Ablauf werden Antworten serverseitig abgelehnt – auch wenn ein manipulierter Client sie sendet.
  • In den DevTools eines Teilnehmers ist die richtige Antwort vor der Auflösung nirgends zu finden.
  • Handy mitten in der Frage sperren, nach der Auflösung entsperren → Client zeigt korrekt den REVEAL-Zustand.

Phase 3 Punkte, Scoreboard & Siegerehrung · ~2–3 Abende

Ziel: Aus dem Durchklick-Spiel wird ein Wettbewerb. Stories: U7, U8, U9.

Aufgaben

  1. scoring.ts: richtige Antwort = Punktwert der Frage (Default 100). Als reine, getestete Funktion – hier ist später der einzige Anbaupunkt für den Speed-Bonus.
  2. Scoreboard-Phase mit echten Daten: Rangliste mit Punkten und Veränderung („+100“), auf dem Laptop groß und vorlesbar.
  3. Spieler-Ansicht: eigener Punktestand permanent sichtbar, eigene Platzierung im Scoreboard hervorgehoben.
  4. FINAL-Ansicht: Top 3 als Siegertreppchen auf dem Laptop, jeder Teilnehmer sieht die eigene Endplatzierung.
  5. Gleichstand-Regel festlegen und umsetzen (Empfehlung: gleicher Rang, alphabetische Anzeige).

Akzeptanzkriterien

  • Punktestände sind über Laptop und alle Handys hinweg jederzeit identisch.
  • Ein Spieler, der eine Frage verpasst (Späteinsteiger oder offline), bekommt 0 Punkte dafür – ohne Fehler im Ablauf.
  • Scoring-Funktion ist vollständig durch Tests abgedeckt (richtig, falsch, keine Antwort, Gleichstand).

Phase 4 Quiz-Editor · ~3–4 Abende

Ziel: Der Quizmaster braucht keine JSON-Dateien mehr von Hand zu schreiben. Story: U1.

Aufgaben

  1. Quiz-Übersicht in der Host-Ansicht: Liste aller Quizzes aus quizzes/, Aktionen: neu, bearbeiten, duplizieren, löschen, „Session starten“.
  2. Editor-Formular: Titel; je Frage Text, 2–6 Optionen, Markierung der richtigen Antwort, Zeitlimit, Punktwert; Fragen sortieren und löschen.
  3. Speichern über kleine REST-Routen (GET/PUT /api/quizzes) in den quizStore; Validierung mit klaren Fehlermeldungen (z. B. „Frage 3 hat keine richtige Antwort markiert“).
  4. Schutz vor Datenverlust: Warnung beim Verlassen mit ungespeicherten Änderungen.

Akzeptanzkriterien

  • Ein 10-Fragen-Quiz lässt sich komplett im Browser anlegen und direkt danach spielen.
  • Unvollständige Fragen können nicht gespeichert werden; die Fehlermeldung benennt die betroffene Frage.
  • Die erzeugte JSON-Datei ist menschenlesbar und von Hand editierbar (Notfall-Weg bleibt offen).

Phase 5 Härtung & Feldtest · ~2–3 Abende + 1 Quizabend

Ziel: Das MVP besteht das Erfolgskriterium: ein echter Quizabend mit ≥ 5 Personen über echten Hotspot, ohne Entwicklereingriff. Story: U10 (Feinschliff) + alles zusammen.

Aufgaben

  1. Reconnect-Härtetest: Flugmodus an/aus, Display lange gesperrt, Browser gewechselt – Spieler muss immer in den aktuellen Zustand zurückfinden.
  2. Host-Neustart-Absicherung: Was passiert, wenn der Laptop-Browser (nicht der Server!) neu lädt? Die Host-Ansicht muss sich wie ein Client reconnecten können.
  3. Join-Hilfe für Teilnehmer: Hinweis auf die „Verbunden, kein Internet“-Meldung (siehe Netzwerk-Stolpersteine).
  4. Mini-Lasttest: Skript, das 40 WebSocket-Clients simuliert, die gleichzeitig beitreten und antworten (30 Zeilen mit dem ws-Paket als Client).
  5. UI-Politur nur, wo es den Abend rettet: Lesbarkeit der Laptop-Ansicht aus 3 m Entfernung, Tap-Flächen auf kleinen Handys, Verbindungsstatus-Anzeige („offline – verbinde neu …“).
  6. Generalprobe: Quizabend mit Freunden/Familie, echter Hotspot, 10 Fragen. Du bist nur Quizmaster, nicht Entwickler. Alle Reibungspunkte notieren.

Akzeptanzkriterien = Definition of Done des MVP

  • Der Feldtest wurde ohne Codeänderung und ohne Server-Neustart durchgestanden.
  • Jeder Verbindungsabbruch im Test endete in erfolgreicher Rückkehr ins Spiel.
  • 40 simulierte Clients: Beitritt und Antworten ohne Fehler, Snapshot-Versand < 500 ms.
  • Die Reibungspunkte der Generalprobe sind als priorisierte Liste im Backlog erfasst.

Gesamtübersicht

Phase Ergebnis („demofähig“) Stories Aufwand
0 · Fundament Handy zeigt live die Server-Uhr über den Hotspot (inkl. Reconnect) – ~2–3 Abende
1 · Lobby Beitritt per QR, Live-Teilnehmerliste U2–U4 ~3–4 Abende
2 · Spielschleife Komplettes Quiz durchspielbar (ohne Punkte) U5, U6 ~4–5 Abende
3 · Scoring Wettbewerb mit Scoreboard und Siegerehrung U7–U9 ~2–3 Abende
4 · Editor Quiz komplett im Browser erstellbar U1 ~3–4 Abende
5 · Feldtest Bestandener echter Quizabend 🏆 U10 + alle ~2–3 Abende + 1 Abend

Durchgängige Arbeitsregeln (Definition of Done je Phase)

  • Alle Akzeptanzkriterien der Phase sind erfüllt und am echten Gerät (Handy im Hotspot) geprüft, nicht nur in zwei Browser-Tabs.
  • Die Engine-/Scoring-Logik der Phase ist mit Vitest getestet; UI wird manuell geprüft (UI-Tests lohnen sich für einen Solo-Dev-MVP nicht).
  • main ist lauffähig, npm start genügt.
  • Neue Erkenntnisse und verschobene Ideen wandern sofort ins Backlog statt in den Code.
Die zwei größten Solo-Dev-Fallen bei diesem Projekt:
  1. UI-Perfektionismus vor Phase 5. Hübsche Animationen sind Backlog. Ein Quizabend scheitert an Reconnect-Bugs, nie an fehlendem Konfetti.
  2. „Nur schnell“ Features aus dem Backlog vorziehen (Teams! Speed-Bonus!). Jede Erweiterung der Spielregeln vervielfacht die Zustände der State-Machine. Erst den Feldtest bestehen, dann erweitern.
